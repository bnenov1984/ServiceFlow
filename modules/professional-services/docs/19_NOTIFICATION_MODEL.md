# PS-19 — Notification Model

Status: **Draft for PO review** · Date: 18.07.2026 · Module: `professional-services`

Module-owned, in-app, deterministic (ADR-PS-009). The platform has no
notification capability today (BOS-02: group D, "do not design in Phase 0")
— so per the build-own-or-wait rule this module builds its own, shaped for
future extraction comparison but private to `ps_*`.

## 1. Entity

`Notification`: company_id, recipient user_id, type, severity
(`info | warning | critical`), assignment_id (nullable for digests),
message_key + params (i18n — never prose), `dedup_key`, created_at,
acknowledged_at, snoozed_until, delivered_channels (MVP: `inapp`).

## 3. Determinism, dedup, lifecycle

- Generated by the same two evaluation paths as the engine ([13] §7):
  morning per-tenant job + on-write recompute. Generation is a pure
  function of (state transitions since last evaluation, config); re-running
  never duplicates — the **dedup_key** is unique per live notification:
  `type:assignment:owner-relevant-state` (e.g.
  `official_deadline_approaching:⟨id⟩:urgent`). A new state (urgent →
  critical) is a new key ⇒ a new notification; re-evaluation of the same
  state hits the unique index and no-ops (FR-PS-091, tested [32] §T-5).
- **Acknowledge**: per-recipient, keeps the record, clears the badge. The
  underlying dashboard bucket is untouched (control stays honest, [13] §7).
- **Snooze-until**: hides that notification until date; state changes
  (worse risk) mint a new key and cut through the snooze.
- Auto-resolve: when the cause disappears (deadline extended, action
  completed), live unacknowledged notifications for its keys are marked
  resolved — no zombie badges.

## 4. Anti-overload design

- Per-user morning **digest cap**: staleness/no-next-action types collapse
  into one digest notification per user per day ("5 преписки без движение")
  linking to the filtered list; only deadline/breach types fire
  individually. This single rule prevents the wall-of-yellow that kills
  notification products.
- Escalations add managers only for breach/persistent-overdue (two rows in
  the table above), nothing else.
- Org defaults + per-user per-type opt-out (FR-PS-092), except breach.
- Severity is data; UI renders critical ≠ dismissible-by-scroll.

## 5. Future channels (P/F)

Email/desktop push ride the platform outbox when Етап-3 infrastructure
exists (P, FR-PS-094); messaging integrations F. Channel fan-out is a
delivery concern appended to the existing record (`delivered_channels`) —
the model above does not change, which is the extraction-readiness we owe
the platform without building it now.
